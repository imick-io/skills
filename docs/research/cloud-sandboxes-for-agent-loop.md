# Cloud sandboxes for the agent loop


> **Context.** Written in October 2026 for one project using these skills (EveryShelf), while its agent loop on Docker Desktop for Mac took over 10 minutes per sandbox install. It first fixed that with `.sandcastle/volumes.mts` there: `node_modules` and the pnpm store in Docker volumes, through a patch to Sandcastle. The template ships the follow-up instead, `isolated-docker.mts` (`AGENTS_SANDBOX=isolated`): the same install speed with no patch, no per-branch volumes, and no way for a sandbox to touch the host checkout. The runtime comparisons below hold either way.

Can a cloud sandbox replace or sit beside local Docker for the imick-io/skills agent loop? The loop runs Claude Code through `@ai-hero/sandcastle` 0.12.0 in Docker on the developer's Mac. The goal is for installs and tests to run on Linux at native disk speed, with no container work on the Mac. Date: 2026-10-30.

## What sandcastle already supports (SC)

- **Built-in isolated providers: Vercel and Daytona.** The README lists only Vercel. The 0.12.0 package also exports `@ai-hero/sandcastle/sandboxes/daytona`, and both are on upstream `main`. No provider exists for E2B, Modal, Fly, Cloudflare or the others. A custom one is about 150 lines through `createIsolatedSandboxProvider`.
- **Isolated contract:** `exec(command, { onLine, cwd })` returning `{stdout, stderr, exitCode}`, `copyIn` (file or directory), `copyFileOut`, `close`, `worktreePath`. Branch strategy `merge-to-head` (the default) or `branch`. `head` is bind-mount only, so the loop's head mode can't run isolated.
- **Gap in `vercel()`:** the provider copies only `source`, `ports`, `resources`, `networkPolicy`, `runtime`/`template`, `timeout`, `env`, `token`, `projectId` and `teamId` into `Sandbox.create()`. **It does not pass `image` or `mounts`**, so a custom image and Drives need a small patch or a custom provider. The repo already patches sandcastle (`patches/@ai-hero__sandcastle@0.12.0.patch`). It also still uses the deprecated `runtime` option.
- **`daytona()`** passes its `create` object straight to `@daytona/sdk`, which covers image or snapshot, resources, env, network and volumes. It streams `exec` through Daytona sessions and copies files with `sandbox.fs.uploadFile`/`downloadFile`. Its peer range is `@daytona/sdk ^0.164.0`, but the current SDK is 0.227.0 (NPM), so expect a peer warning or pin.
- **Secrets:** both built-in providers pass the run's env (from `.sandcastle/sandbox-env` and agent env) as plain environment variables inside the VM.

## Findings that matter for this loop

1. **Disk speed is already solved locally.** `.sandcastle/volumes.mts` keeps the pnpm store and `node_modules` in Docker volumes inside the Docker VM, which brought an install from over 10 minutes to about 15 s. A cloud sandbox would mainly free the Mac's CPU, RAM and battery, let the loop run with the lid closed, and allow more parallelism. It would not make installs much faster.
2. **The pnpm cache takes a different shape in the cloud.** There is no shared read-write volume across six live sandboxes on Vercel (one read-write mount per Drive) or E2B (beta). The practical pattern is to bake the pnpm store into the image or a snapshot. Rebuild it nightly, or have one writer refresh a Drive and give readers `drive.snapshot()` mounts (VSB). Daytona volumes allow shared read-write, but they are FUSE/S3 and slow on many small files (DAY).
3. **The image works in every VM-based option as long as it is `linux/amd64`.** Postgres 18, PostGIS, pgvector, Redis, Playwright and Claude Code all live in one image, and the loop already starts services from a script (`sandbox-services.sh`) rather than `ENTRYPOINT`. That suits Vercel, which ignores `ENTRYPOINT` (VSB). On an Apple-silicon Mac the image must be cross-built or built in GitHub Actions; VCR has a login action (VSB). Cloudflare is the odd one out: you must extend its base image, and the disk is wiped on sleep (CF).
4. **Secrets can stay out of the VM.** Vercel's firewall `transform` (VSB), Daytona's placeholder secrets (DAY) and E2B's `Secret.fill` (E2B) inject `ANTHROPIC_API_KEY` or `GH_TOKEN` at egress. Sandcastle doesn't use any of these yet; it passes env vars. Because isolated mode returns commits as format-patch files, the sandbox never needs a push token.
5. **Egress:** all three leading options can allowlist `github.com`, `*.githubusercontent.com`, `registry.npmjs.org` and `api.anthropic.com`. Daytona Tier 1–2 accounts are locked to its allowlist and can't override it per sandbox. Tier 1 is also capped at 10 vCPU total, which is too small for 6 × 4 vCPU (DAY).
6. **Session length:** every serious option allows at least 90 minutes on a paid plan. Free tiers do not: Vercel Hobby allows 45 min and E2B Hobby 1 h, so a free account will cut runs short.

## Recommendation

**Keep local Docker as the template's default and add one cloud provider as an opt-in mode. Make that provider Vercel Sandbox.**

- **Why local stays the default:** it costs nothing, needs no account or billing setup for someone adopting the template, already has fast installs through volumes, supports head mode, and the loop's volume and sweep logic is built around it.
- **Why Vercel for the cloud mode:**
  - It already ships in sandcastle.
  - It runs the existing Dockerfile as a custom OCI image.
  - Sessions last 24 h on Pro.
  - It bills **active CPU**, which suits agents that mostly wait on the model and makes it the cheapest managed sandbox here (~$270/month for the workload above).
  - It has the most complete egress firewall, with credential brokering.
  - Snapshots and Drives can keep the pnpm store warm.
- **Cost of adopting it:** a small sandcastle patch so `vercel()` forwards `image`, and optionally `mounts`; the same fix should go upstream. You'd also need an amd64 image build in CI, a nightly snapshot or Drive refresh for the pnpm store, and a cloud branch in `.sandcastle/main.mts` that skips the Docker volume code.
- **Runner-up: Daytona.** It already has a sandcastle provider with full passthrough, the same headline rates as E2B and proxy-based secrets. But the 4 vCPU / 8 GB / 10 GB-disk cap is tight for Playwright plus Postgres plus `node_modules`, and the Tier 1–2 network and quota limits rule it out for a new account.
- **E2B** works but costs about $500/month once you add the $150 Pro fee and provisioned-CPU billing.
- **Modal's** JS SDK is still beta and its sandbox rates are 3× its base rates.
- **Not a fit:** Fly Machines (exec doesn't stream), Sprites (no custom image), Cloudflare (Worker-bound, disk wiped on sleep), Codespaces (no exec SDK), and Depot and Runloop (immature or expensive for this use).
